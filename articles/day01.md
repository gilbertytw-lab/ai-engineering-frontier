# AI Engineering 研究前線：30 天讀懂一週一週長出來的技術脈絡

## Day 1：先把本地 AI 專案的邊界畫清楚

今天沒有寫模型呼叫程式。

我先做 Git init，然後把這個 30 天專案到底要交付什麼寫下來。這一步看起來不太像在做 AI，但我目前最怕的不是模型跑不起來，而是跑起來之後不知道哪一層出了問題。

如果你只用過 ChatGPT、Claude 或 Gemini 這類網頁對話式 AI，第一次在自己的電腦上架設本地系統，很容易先去裝模型、向量資料庫、Agent framework 和 Web UI。每個工具都像是必要條件，最後卻還是不知道文件為什麼沒被找出來，或模型為什麼把沒有出現過的答案講得很肯定。

所以我先把目標縮小。

## 30 天後要留下什麼

這個專案叫做 Local Engineering Knowledge Assistant。讀者把自己的 Markdown 或文字文件放進去，提出問題，系統從文件找證據，再交給本地模型回答。

最小版本要做到這些事：

- 能在本地呼叫模型。
- 能讀取自己的文件並建立可重建的索引。
- 能在固定的 context 預算內挑選證據。
- 回答附上來源，找不到證據時就說找不到。
- 能完成至少一項唯讀的知識操作。
- 有一組固定問題，可以比較每一版的回答品質、token 使用量和執行時間。

我沒有把「功能越多越好」放進完成條件。對第一次做本地 AI 的人來說，知道這段回答用了哪份文件，比多一個花俏的按鈕實在。

## 先不做的東西

30 天要完成一套能跟著做的系統，範圍不能一直長大。因此模型訓練、多 Agent、開放式 shell、任意修改檔案，以及需要雲端服務才能啟動的部署，都先放到核心目標外面。複雜 GraphRAG 和大型向量資料庫也一樣。

這不是說它們不重要，只是現在加入會讓除錯變得很混亂。第一版先把模型、文件、檢索和回答這幾層分開，遇到問題才知道要查哪裡。

## 我目前選的資料流

文件先保存在 `knowledge/raw/`。這裡的內容是之後查證的根據，不因為建立索引就丟掉。接著留下文件版本、雜湊值和切分紀錄；需要給人看的整理，放到知識頁；給機器查詢的 FTS 或 embedding index 則視為可以刪掉重建的產物。

```text
knowledge/raw
  → 文件版本、雜湊值與切分紀錄
  → 可讀的知識頁（選用）
  → 檢索候選
  → context 預算與證據組裝
  → 本地模型
  → 附來源回答或明確拒答
```

本地模型的 context 很珍貴，所以不會把整個知識庫一股腦塞進每次請求。整理頁可以幫忙導覽，真正支撐答案的還是能回到原始文件的證據。這個取捨會在後面的 RAG 實驗裡驗證，不先把它當成結論。

我現在用的是 macOS 26.6、arm64、Python 3.9.6 和 Git 2.50.1。`uv` 還沒裝，今天也不打算為了湊齊工具清單先停下來。等 Day 2 要寫模型呼叫時，再依照選定的 runtime 決定環境怎麼建。

之後每天會留一筆可以執行或驗證的變更。讀者不需要等到 Day 30 才知道前面做了什麼，也可以在任一天切回當時的版本。

## 這個專案怎麼保持原創

名稱、資料流、目錄、模組、範例文件、文章和程式碼都從這個專案的讀者與限制重新決定。外部文件只在真的用到時登錄來源，不搬用別人的程式碼、段落、Prompt、圖片、示範案例或文章排列方式。

我另外把設計決策、來源和發文前檢查分開記在 `docs/`。這樣日後有人問「為什麼這樣切資料層」，我可以回到當時的決策，而不是用最後完成的架構倒推一個漂亮故事。
