# AI Engineering 研究前線：30 天讀懂一週一週長出來的技術脈絡

## Day 1：先把本地 AI 專案的邊界畫清楚

如果你只用過 ChatGPT、Claude 或 Gemini 這類網頁對話式 AI，那麼第一次在自己的電腦上架設本地模型，很可能會一頭霧水：

### 為什麼這麼難用！？

覺得難用可能還是小問題，大多數人甚至完全不知道下一步要做什麼．

所以讓我們從頭開始，從下載安裝本地模型到可以正常對話、讀寫檔案，最後建成本地知識庫管理員．

GitHub Repo: https://github.com/gilbertytw-lab/ai-engineering-frontier.git

## 30 天後要留下什麼

這個專案叫做 Local Engineering Knowledge Assistant。讀者把自己的 Markdown 或文字文件放進去，提出問題，系統從文件找證據，再交給本地模型回答。

由於硬體限制，本地模型的 context 很珍貴，所以我們不能將整個知識庫塞進每次請求。整理頁可以幫忙導覽，真正支撐答案的還是能回到原始文件的證據。這個取捨會在後面的 RAG 實驗裡驗證，不先把它當成結論。

## 今天的環境

我現在用的是 macOS 26.6、arm64、Python 3.9.6 和 Git 2.50.1。查完 [Python 官方版本狀態](https://devguide.python.org/versions/) 後，3.9 不會拿來當這個專案的 Python 基線；Day 2 會改用 Python 3.13.x 建立隔離環境。`uv` 還沒裝，今天也不打算為了湊齊工具清單先停下來。等要寫模型呼叫時，再依照選定的 runtime 決定環境怎麼建。

今天已經建立 Git repository，第一筆 commit 是：

```text
b315d9d day01: define project scope
```

之後每天會留一筆可以執行或驗證的變更。讀者不需要等到 Day 30 才知道前面做了什麼，也可以在任一天切回當時的版本。

## 這個專案怎麼保持原創

名稱、資料流、目錄、模組、範例文件、文章和程式碼都從這個專案的讀者與限制重新決定。外部文件只在真的用到時登錄來源，不搬用別人的程式碼、段落、Prompt、圖片、示範案例或文章排列方式。

我另外把設計決策、來源和發文前檢查分開記在 `docs/`。這樣日後有人問「為什麼這樣切資料層」，我可以回到當時的決策，而不是用最後完成的架構倒推一個漂亮故事。

## 今天到這裡

今天的產出不是一個能回答問題的模型，而是一個有範圍、有環境紀錄、可以繼續長大的 repository。
