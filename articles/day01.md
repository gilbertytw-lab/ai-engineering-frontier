# AI Engineering 研究前線：30 天讀懂一週一週長出來的技術脈絡

## Day 1：先把本地 AI 專案的邊界畫清楚

如果你只用過 ChatGPT、Claude 或 Gemini 這類網頁對話式 AI，第一次想在自己的電腦上架設 AI 系統時，很容易從安裝一大堆工具開始：模型、向量資料庫、Agent framework、Web UI、監控服務，每一項看起來都不可或缺。

但真正開始後，問題通常不是工具太少，而是不知道每一個工具要解決什麼問題。這個 30 天系列的第一天不急著呼叫模型，也不急著選框架。我們先把最後要交付的東西說清楚，讓之後每天的程式變更都有可以驗證的方向。

## 我們要完成什麼？

這個系列的目標是建立一個可以在本地執行的工程知識助理。它不是要取代通用聊天服務，而是讓使用者把自己的 Markdown 或文字文件放進系統，接著用自然語言詢問文件中的內容。

30 天後，最小可行版本應該能做到以下事情：

- 在本地呼叫一個語言模型。
- 讀取使用者自己的文件。
- 將原始文件建立成可以重建的索引。
- 只挑選與問題相關的證據放進模型的 context。
- 回答時標示來源，找不到足夠證據時明確說明不知道。
- 執行至少一項受限制的唯讀知識操作。
- 用固定問題集比較系統的回答品質、token 使用量與執行時間。

這個目標刻意不把「功能最多」當成成功標準。對第一次嘗試本地 AI 的讀者來說，能夠理解資料從哪裡來、為什麼被選進回答，以及系統在什麼時候應該拒答，比加入更多按鈕更重要。

## 目標讀者與學習方式

本系列假設讀者有使用網頁對話式 AI 的經驗，但不假設讀者已經了解 Transformer、向量資料庫、Agent framework 或模型訓練。每一天只增加一個必要能力，並在文章結尾留下可執行的結果、Git commit 與下一天的問題。

學習路線會從最小的本地模型呼叫開始，先建立可以重複執行的聊天流程；接著加入自己的文件、文件整理、檢索與 context 預算控制；最後才加入唯讀工具、任務限制與評估。這個順序不是為了追求名詞完整，而是讓每一次變更都能回答一個具體問題：上一版哪裡不夠，今天加入的東西如何改善它？

## 第一版刻意不做什麼？

30 天並不足以把所有 AI Engineering 主題都做成可靠產品，因此以下項目不列入核心完賽條件：

- 模型訓練或微調。
- 多 Agent 協作。
- 開放式 shell 執行。
- 讓模型任意修改使用者檔案。
- 需要雲端服務才能啟動的部署。
- 複雜的 GraphRAG 或大型向量資料庫維運。

這些主題未必沒有價值，但如果太早加入，讀者很難判斷問題來自模型、資料、檢索、工具還是部署環境。第一版先保留清楚的責任邊界，之後再用實驗結果決定哪些延伸功能值得加入。

## 今天確定的資料流

本專案會把資料分成三種責任：原始文件是可追溯的來源；整理後的知識頁負責人類閱讀與導覽；FTS 或 embedding 索引則是可以刪除後重建的機器查詢資料。最後由 context 組裝器在固定預算內選取少量證據，再交給本地模型回答。

```text
原始文件
  → 文件版本與切分紀錄
  → 可讀的知識頁（選用）
  → 檢索候選
  → context 預算與證據組裝
  → 本地模型
  → 附來源回答或明確拒答
```

這條資料流是依照本專案的兩個限制推導出來的：第一，初學者需要一條可以逐步完成的路徑；第二，本地模型的 context 有限，不能把整個知識庫不加選擇地放進每一次請求。後續所有架構變更，都要說明它如何改善這兩個限制之一。

## 今天的環境基線

目前使用的開發環境是 macOS 26.6、arm64、Python 3.9.6 與 Git 2.50.1。`uv` 尚未安裝，今天不讓套件管理工具成為進度的前置條件；等到需要建立模型呼叫程式時，再根據 runtime 選擇適合的環境管理方式。

今天也建立了 Git repository。從現在開始，每一天都會留下可讀的變更與結果，讓讀者能夠在任何一天從乾淨的 commit 重新開始，而不是只能閱讀最後完成的程式。

## 原創性與可追溯性

本系列的專案名稱、資料流、目錄、模組、範例文件、文章與程式碼都從本專案的目標讀者和限制重新設計。外部文件只在實際使用時記錄來源，不直接搬用段落、程式碼、圖片、Prompt、示範案例或文章結構。

Repository 裡的 `docs/design-decisions.md` 會記錄架構為什麼這樣選，`docs/sources.md` 會記錄真正使用到的外部資料，`docs/originality-check.md` 則會在每天發文與正式 release 前逐項檢查。這些文件不是附加工作，而是讓 30 天的產出能夠證明每一步如何獨立形成。

## Day 1 的完成狀態

今天完成了專案範圍、目標讀者、非目標、環境基線與 Git 起點。現在還沒有模型可以呼叫，這是刻意的：Day 1 的成果是把問題定義正確，而不是先產生一段無法解釋的輸出。

下一天只處理一件事：在本地成功呼叫模型，並記錄模型、runtime、硬體與最小輸入輸出結果。
